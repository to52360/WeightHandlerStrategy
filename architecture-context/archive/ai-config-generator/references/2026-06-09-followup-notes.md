# 后续问题记录 - ai-config-generator

## 2.1 引用数据描述与分类

待评估问题：

- AI 生成评估树时引用的数据是否都需要 `description` 字段。
- 条件是否需要 `category` 和 `categoryDesc`。
- 规则、条件树、评估树、卡组/用途标签等其他引用对象是否也需要分类。

初步边界：

- `description` 更偏向 AI/作者侧理解，优先属于 configUi/MCP 暴露模型，不应直接变成引擎热路径依赖。
- `category` 只有在“检索候选项明显过多，需要先缩小范围”时才有价值；否则会变成维护负担。
- 条件和规则是 AI 最容易选错的原子能力，分类收益最大；评估树/条件树是否分类要看它们是否会作为可复用模板被 AI 检索。

## 2.2 评估树模板与正式数据共表

待评估问题：

- `tree_config` 同时保存模板和正式数据是否会污染引擎启动绑定。
- `is_template` 是否足够表达模板身份，是否还需要模板来源、适用范围、版本等字段。
- UI 与 MCP 保存时是否默认只保存正式数据，模板需要独立 tool 或参数。

初步边界：

- 共表可以接受，但所有运行期 provider 必须明确排除模板。
- 如果模板也需要绑定示例，绑定不能被运行期消费，只能被 UI/MCP 当作生成提示或默认值。

## 2.3 AI 生成条件逻辑

只记录方向，暂不展开：

- 后续可以让 AI 生成 `ConditionTreeConfig` 或更细的条件逻辑。
- 这会引入更高风险的条件引用、参数作用域、条件树复用和校验问题。
- 当前阶段先聚焦评估树生成，不把条件逻辑生成混进最小 MCP 链路。
