# 架构探讨：评估树中的“算分”与“控制”职责分离及规则正交化

在 T-002 任务的落地过程中，我们发现目前的策略评估树叶子节点（`EvaluatorLeafConfig`）同时承载了**算分（Scoring）**与**
控制（Control/Action）**两重职责。同时，“条件”作为纯 Boolean 逻辑，在被评估树叶子节点包装时被赋予了权重属性，引发了关于职责边界的深层思考。

以下是对该问题的多 agent 架构盲审与讨论方案：

---

## 1. 现状痛点分析

### 1.1 算分与控制的物理耦合

目前评估树叶子节点执行后，返回的是 `RuleResult.Continue(score, modifyCard)`。

- **算分（Scoring）**：用来决定这张出牌的“权重得分”（即好坏程度），分值会累加。
- **控制（Control/Action）**：用来对出牌动作施加具体干预（如指定 `pointCard` 目标，或者绑定 `useGroupId` 协同出牌）。
  这导致了职责耦合：
- 如果一个节点只想执行**控制**（例如“若手牌有随从，则将指向目标设为敌方英雄”），它必须被迫声明 `weight` 和
  `mismatchedWeight`；
- 如果一个节点只想做**纯粹的数值评分加减**（如“手牌每多一张，评分加 0.5”），它又带着无用的 `modifyCard` 结构。

### 1.2 条件作为叶子节点时的“被迫算分”

用户指出“条件不触碰算分”。但在当前设计中，`EvaluatorLeafSourceType.CONDITION` 允许直接将一个 Boolean 条件作为评估树叶子节点，引擎会用
`toWeightedRuleLogic` 强行赋予其 `weight`。这使得配置端在配置一个“条件”时，必须同时在叶子节点上配置“算分”权重，使得条件与算分的边界变得模糊。

---

## 2. 演进方案设计提案

为了实现彻底的关注点分离，并为后续“Rule 的正交化（数据与算子）”作准备，我们提出以下三种架构方案：

### 方案一：评估树叶子多态化 —— 显式拆分“评分叶子”与“控制叶子”

不再使用单一的 `EvaluatorLeafConfig` 表达所有概念，而是在评估树层面将叶子节点进行多态拆分：

1. **评分叶子（ScoreLeaf）**：
    - 职责：只负责评分。
    - 配置项：`baseScore: Double`、`multiplierSourceId: String?`（动态乘数数据源）。
    - 返回：纯 `Double` 分值。
2. **控制叶子（ControlLeaf）**：
    - 职责：只负责输出控制决策。
    - 配置项：`actionType: ActionEnum`、`actionArgs: Map<String, Any>`。
    - 返回：`ComboCardAction`（例如设置指向、协同分组等）。

*评估树的执行结果是将评分叶子的分值进行累加，并将控制叶子的控制动作进行合并（Merge）。*

---

### 方案二：规则（Rule）正交化 —— 消除硬编码 Rule 类

目前 `Condition` 已经通过 `DataSource + Operator` 实现了正交化，但 `Rule` 仍然是硬编码的 Kotlin 类。我们可以借鉴正交化思想，将
`Rule` 彻底配置化：
$$\text{Rule} = \text{Guard Condition (条件树)} + \text{Score Effect (评分效应)} + \text{Control Action (控制动作)}$$

在配置端，一个 Rule 的元数据包括：

- **Guard**：引用一个 `ConditionTree`（纯 Boolean 判定）。
- **ScoreEffect**（可选）：
    - 静态分值：加/减 $X$ 分；
    - 动态分值：乘以 $Y$ 数据源。
- **ControlAction**（可选）：
    - 动作类型：指向随从/英雄、协同分组、排序策略等。

**引擎层执行流程**：

1. 评估 `Guard` 条件，如果为 `false`，则不施加任何效应。
2. 如果为 `true`：
    - 执行 `ScoreEffect` 计算分值并累加；
    - 执行 `ControlAction` 生成控制动作指令并合并。

*此方案能彻底消灭硬编码的 Rule 类，实现 100% 的配置驱动。*

---

### 方案三：Guard 守卫模式 —— 评估树只组合 Rule，Condition 仅作为 Rule 的前提

评估树的叶子节点**只能**是 `Rule`（无论硬编码 Rule 还是未来的正交 Rule），`Condition` 和 `ConditionTree`
不再允许作为评估树的叶子节点独立存在。

- 如果想根据某个条件算分，必须配置一个 `Rule`，在这个 `Rule` 的属性中配置 `guardCondition = conditionTreeId` 以及相应的分数。
- 这样，条件在配置端和引擎端都退回到了纯粹的“逻辑守卫”职责，完全不感知、不触碰任何评分与控制配置。
