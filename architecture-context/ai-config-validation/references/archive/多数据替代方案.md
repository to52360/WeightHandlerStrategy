我同意你的直觉：**方案 Z 不够好**。它的问题不是跑不通，而是把“多事件来源的业务语义”塞进一个复合 DataSource，DataSource 变成了小型聚合器，边界开始发虚。

但我也不建议现在直接上“通用多数据源管道”。当前 `PipelineRef` 是：

```kotlin
sourceId -> transforms[] -> operator
```

`PipelineAssembler` 的校验、装配、UI/MCP 元数据都假设一条线性类型链。改成多数据源，本质是引入表达式/DAG：

```kotlin
sum(
  pipeline(match_group_played_counts -> pick_group_count(...)),
  pipeline(graveyard_cards -> filter_card_ids(...) -> count_projection)
) >= 4
```

这方向长期更干净，但对 Q-2a 来说太大，容易从“圣契条件建模”滑到“重写正交表达式系统”。

我更倾向第三条路：**新增一个领域中立的事件流 DataSource，不是复合快照，也不是多 DataSource DAG**。

最小模型大概是：

```kotlin
enum class MatchActivityKind {
    CARD_PLAYED,
    CARD_GRAVEYARD
}

data class MatchActivityEvent(
    val kind: MatchActivityKind,
    val cardId: String,
    val groupIds: Set<String>
)

class MatchActivityEventsSource : DataSource<List<MatchActivityEvent>> {
    override val id = "match_activity_events"

    context(env: RuleEnv)
    override fun resolve(context: RuleContext): List<MatchActivityEvent> {
        return buildList {
            addAll(env.matchState().playedEvents())
            addAll(env.warView.my.getGraveyardCards().map { card ->
                MatchActivityEvent(
                    kind = MatchActivityKind.CARD_GRAVEYARD,
                    cardId = card.cardId,
                    groupIds = env.cardGroupIndex().groupsOf(card.cardId)
                )
            })
        }
    }
}
```

然后参数化 Transform 负责业务配置：

```kotlin
data class WeightedActivitySumParams(
    val rules: List<ActivityWeightRule>
)

data class ActivityWeightRule(
    val kind: MatchActivityKind,
    val cardIds: List<String> = emptyList(),
    val groupIds: List<String> = emptyList(),
    val weight: Int
)

val WeightedActivitySumTransform:
    Transform<List<MatchActivityEvent>, Int>
```

配置表达：

```text
match_activity_events
  -> weighted_activity_sum([
       { kind=CARD_PLAYED, cardIds=[GDB_726], weight=1 },
       { kind=CARD_GRAVEYARD, cardIds=[GDB_726], weight=1 },
       { kind=CARD_PLAYED, cardIds=[GDB_728,...], weight=1 }
     ])
  -> gte(4)
```

这个方案和 Z 的关键差别：

- DataSource 只负责暴露“对局活动事件流”，不懂圣契、不懂权重、不懂阈值。
- Transform 才负责“按 cardId/groupId + 事件类型 + 权重求和”，参数全来自配置。
- 仍然保持 `PipelineRef` 单源线性，不动 AST/UI/MCP 主结构。
- 比 `MatchActivitySnapshot` 更像领域事实模型：不是“为了这条规则临时凑的快照”，而是可复用的事件流。
- 后续如果有“某牌死亡次数”“某组本局活动次数”“打出或死亡任一达到 N”也能复用。

我会把多数据源管道暂时列为 **后续表达式系统升级候选**，不是 Q-2a 的首选解。Q-2a 当前更应该收敛成：

> 单源仍保留，但这个单源不是方案 Z 的复合统计结果，而是 `match_activity_events: List<MatchActivityEvent>`；所有业务筛选、权重、阈值留在参数化 Transform / Operator。

还剩一个真实未决点：`MatchState` 现在主要是 count，如果要输出 `playedEvents()`，需要确认它是否保存“按 cardId 的打出事件/计数 + groupIds”。如果没有，就补成事件或至少补 `allCardPlayCounts()`，再在 DataSource 展开成事件流。这里比改多数据源小很多。




对，`weighted_activity_sum` 是 **Transform**。

关键点是：**Transform 只有一个运行时输入和一个输出，但它还可以有配置参数**。我前面说的形状不是“多个输入”，而是：

```kotlin
DataSource 输出: List<MatchActivityEvent>
Transform 输入: List<MatchActivityEvent>
Transform 参数: WeightedActivitySumParams
Transform 输出: Int
Operator 输入: Int
```

也就是：

```text
match_activity_events
  -> weighted_activity_sum(params)
  -> gte(4)
```

最小模型：

```kotlin
data class MatchActivityEvent(
    val kind: MatchActivityKind,
    val cardId: String,
    val groupIds: Set<String>
)

data class WeightedActivitySumParams(
    val rules: List<ActivityWeightRule>
)

data class ActivityWeightRule(
    val kind: MatchActivityKind,
    val cardIds: List<String> = emptyList(),
    val groupIds: List<String> = emptyList(),
    val weight: Int
)

val WeightedActivitySumTransform =
    transform<List<MatchActivityEvent>, Int, WeightedActivitySumParams>(
        id = "weighted_activity_sum",
        name = "活动加权求和"
    ) { events, params ->
        events.sumOf { event ->
            params.rules
                .filter { rule -> rule.matches(event) }
                .sumOf { rule -> rule.weight }
        }
    }
```

所以它的“形状”不是：

```text
Transform(matchStateInput, graveyardInput) -> Int
```

而是：

```text
Transform(activityEvents, weightRules) -> Int
```

其中：

- `activityEvents` 是唯一输入，来自 DataSource。
- `weightRules` 是配置参数，不是第二个数据源。
- `Int` 是输出，交给 `gte(4)` 判断。

圣契配置表达的是参数，不写死 Kotlin：

```json
{
  "sourceId": "match_activity_events",
  "transforms": [
    {
      "transformId": "weighted_activity_sum",
      "args": {
        "rules": [
          { "kind": "CARD_PLAYED", "cardIds": ["GDB_726"], "weight": 1 },
          { "kind": "CARD_GRAVEYARD", "cardIds": ["GDB_726"], "weight": 1 },
          { "kind": "CARD_PLAYED", "cardIds": ["GDB_728"], "weight": 1 }
        ]
      }
    }
  ],
  "operatorId": "gte",
  "operatorArgs": { "threshold": 4 }
}
```

不过这里有个现实限制要注意：当前 `FieldParser` 对 `List<ActivityWeightRule>` 这种“对象列表参数”的 UI/MCP 描述能力可能不够成熟。概念上它是对的，但落地时可能要再收敛参数形状，比如先做成：

```kotlin
data class WeightedActivitySumParams(
    val playedCardWeights: Map<String, Int>,
    val graveyardCardWeights: Map<String, Int>,
    val playedGroupWeights: Map<String, Int> = emptyMap(),
    val graveyardGroupWeights: Map<String, Int> = emptyMap()
)
```

这样仍然是一个 Transform：

```text
List<MatchActivityEvent> + 参数化权重表 -> Int
```

我更建议我们把核心方案表述成：

> `match_activity_events` 只产出事件流；`weighted_activity_sum` 是单输入 Transform，通过参数描述 cardId/groupId + eventKind 的权重规则，输出 Int；`gte` 负责阈值判断。

这样你可以把它理解成“先把多来源统一成一种领域事件，再在线性管道里做参数化聚合”，不是“Transform 支持多输入”。
