## 背景与设计目标

在动态管道（Pipeline）评估中，不同卡牌评估树或不同逻辑分支经常包含 **全同**或 **共享前半段**的管道条件（例如：多个条件都需要统计
`match_activity_events` 经过 `weighted_activity_sum` 筛选后的事件加权和）。

### 核心痛点与现有方案问题

1. **以 `refId` 为 Key 的失效方案**：同一个逻辑管道在配置树中可能被赋予不同的 `refId`（如 `ref_treeA_node1` 与
   `ref_treeB_node2`），导致无法命中缓存。
2. **将 Cache 下沉至组件内部（如 D-9 装饰器）的架构越界**：`Transform` 和 `DataSource`
   组件是原子黑盒，不知道自己在管道链中的具体位置与前置链全貌，强制组件做缓存会导致极其复杂的引用传递、隐式契约脆弱及高昂的代码侵入。

### 本方案核心设计原则（D-12）

1. **闭包层接管（Closure-Level Encapsulation）**：所有的缓存存取与 Key 拼装 **完全封装在 `PipelineAssembler.assemble`
   闭包内部**。`DataSource`、`Transform`、`Operator` 接口及实现零侵入、零改动。
2. **内容哈希替代 `refId`（Content-Hash Keying）**：Key 由 `sourceId` + `transforms` 序列及规范化参数的内容哈希决定。即使
   `refId` 不同，只要逻辑全同即可 100% 命中缓存。
3. **分段累积缓存（Step-wise Incremental Caching）**：
    - **Source 级缓存 Key**：`pipe:src:${sourceId}`
    - **Transform 步阶 Key**：`pipe:step:${cumulativeContentHash}`（其中累积哈希覆盖前置 Source + 截至当前 Step 的所有
      Transform 及参数）
    - **共享前半段复用**：`Pipeline_A` (Src -> Tf1 -> Tf2) 与 `Pipeline_B` (Src -> Tf1 -> Tf3) 评估时，`Pipeline_B` 执行到
      Step 1 时自动命中 `Pipeline_A` 算好的 Step 1 结果，仅执行 Step 2 (Tf3)。

## 架构设计细节

### 1. 规范化参数哈希生成算法 (Canonical Hash)

为了确保 Map 参数如 `{ "a": 1, "b": 2 }` 与 `{ "b": 2, "a": 1 }` 能够稳定生成一致的 Key，对 `args` Map 进行规范化序列化：

```kotlin
private fun canonicalArgsString(args: Map<String, Any>): String {
    if (args.isEmpty()) return ""
    return args.entries
        .sortedBy { it.key }
        .joinToString(separator = ",", prefix = "{", postfix = "}") { (k, v) ->
            "$k:${canonicalValueString(v)}"
        }
}

private fun canonicalValueString(value: Any): String {
    return when (value) {
        is Map<*, *> -> {
            @Suppress("UNCHECKED_CAST")
            canonicalArgsString(value as Map<String, Any>)
        }
        is List<*> -> value.joinToString(separator = ",", prefix = "[", postfix = "]") { 
            canonicalValueString(it ?: "null") 
        }
        else -> value.toString()
    }
}
```

### 2. 预计算步骤 Key (Pre-calculated Step Keys at Assembly Time)

在 `PipelineAssembler.assemble(ref)` 执行时（即规则编译阶段），一次性计算好各 Step 的 Key 字符串，避免在单回合数千次规则评估中进行字符串拼接和哈希计算：

```kotlin
// 1. Source 阶段 Key
val sourceKey = "pipe:src:${ref.sourceId}"

// 2. Transform 阶段分段 Key 列表
val cumulativeBuilder = StringBuilder(ref.sourceId)
val stepKeys = ref.transforms.map { call ->
    cumulativeBuilder.append("->").append(call.transformId)
    if (call.args.isNotEmpty()) {
        cumulativeBuilder.append("(").append(canonicalArgsString(call.args)).append(")")
    }
    // 使用预拼接的内容摘要作为 Key
    "pipe:step:" + cumulativeBuilder.toString()
}
```

### 3. 装配闭包内部缓存执行逻辑

`PipelineAssembler.kt` 中的 `assemble` 方法改造如下：

```kotlin
return { env -> // RuleContext.(RuleEnv) -> Boolean
    // Step 0: Source 查找与缓存
    var currentVal: Any = env.cache(sourceKey) {
        source.resolve(this, env)
    }

    // Step 1~N: Transform 分段链式求值与缓存
    for (i in transformInstances.indices) {
        val (transform, args) = transformInstances[i]
        val stepKey = stepKeys[i]
        currentVal = env.cache(stepKey) {
            transform.transform(currentVal, args)
        }
    }

    // Step N+1: Operator 计算（微秒级比较运算，直接求值）
    operator.evaluate(currentVal, parsedOperatorParameter)
}
```

## 验证计划

### 自动化测试 (Automated Unit Tests)

运行 `mvn -pl WeightHanderStrategy test` 验证以下场景：

1. **`testFullPipelineContentHashCacheHit`**：创建两个 `refId` 不同的 `PipelineRef`（内容完全一致），验证第二个
   `PipelineRef` 执行时，`DataSource.resolve` 和 `Transform.transform` 均只被调用一次。
2. **`testPartialPipelinePrefixCacheHit`**：创建 `Pipeline_A` (Src -> Tf1 -> Tf2) 和 `Pipeline_B` (Src -> Tf1 -> Tf3)
   ，先后评估，验证 `Pipeline_B` 评估时 `Src` 和 `Tf1` 命中缓存（总调用次数为 Src:1, Tf1:1, Tf2:1, Tf3:1）。
3. **`testDifferentArgsCacheMiss`**：验证当 Transform 参数不一致时（如 `threshold: 3` vs `threshold: 4`），缓存产生 Key
   隔离，不发生误命中。
4. **`testRuleEnvIsolation`**：验证当创建新的 `WarInfoEnv` 实例时，缓存隔离并重新触发求值。

## 用户审核事项

> [!IMPORTANT]
>
> 1. **零架构侵入性**：此方案完全不需要修改任何 `DataSource` / `Transform` / `Operator` 现有代码，亦无需扩展领域模型接口。
> 2. **极致编译期优化**：Key 字符串在规则树装配编译阶段（`PipelineAssembler.assemble`）已预先拼装完成，运行期评估仅做 Map
     Key 查找（$O (1)$ 复杂度），没有任何动态字符串拼接成本。
