## 一、现在缓存机制全貌

当前系统有 **两套独立缓存**：

### 1. `PipelineCache`（本局缓存）

- 位置：`MyWarManage.pipelineCache`，Koin 单例
- 生命周期：整局（`GameLifecycle.start()` 清空）
- 用途：原本是 Q-2a 给 `WeightedActivitySumTransform` 内嵌缓存用的，T-127 后该职责已移交 MemoizeStore，
  **目前实际上已经没有正交组件在用它**（只有历史残留）

### 2. `MemoizeStore`（评估内 memoize 缓存）—— T-127 的核心

```
评估开始
  └─ 创建 RuleEnv（WarInfoEnv）
       └─ memoizeStore() → 应返回同一个 MemoizeStore 实例
            └─ 规则树 A 执行：Source.resolve → 缓存入池
            └─ 规则树 B 执行：相同 Source cacheKey 命中 → 返回同一引用
                 └─ Transform 用 identityHashCode(input) 命中 → 级联复用
评估结束 → RuleEnv 回收 → MemoizeStore 随之回收
```

**cacheKey 设计**： | 组件 | cacheKey | 说明 | |---|---|---| | Source（不依赖 callCard） | `src:$id:$envVersion` |
跨规则树/跨卡复用 | | Source（依赖 callCard） | `src:$id:$envVersion:$callCardId` | 避免跨卡错误复用 | | Transform |
`tf:$id:${args.hashCode()}:${System.identityHashCode(input)}` | 用引用 identity，零成本 | | Operator | 不缓存 |
纯比较零成本 |

**链式级联失效**：上游 cacheKey 变 → 返回新 List 引用 → 下游 `identityHashCode(input)` 跟着变 → 整条链自动失效。

**装配流程**（`PipelineAssembler.assemble`，`PipelineAssembler.kt:99-129`）：

```
rawSource.memoize? → rawSource.memoized() → 装入闭包
rawTransform.memoize? → rawTransform.memoized() → 装入闭包
闭包执行：source.resolve → transform.transform → operator.evaluate
```

## 二、发现一个致命 Bug：memoize 机制实际上完全没生效

`RuleContext.kt:26` 和所有测试 fake 里：

```kotlin
// 生产代码 WarInfoEnv
override fun memoizeStore(): MemoizeStore = MemoizeStore()  // ← 每次调用返回新实例！

// 测试 FakeRuleContext.kt:154
override fun memoizeStore() = MemoizeStore()  // ← 同样的 bug

// 测试 MatchActivityPipelineTest.kt:115
override fun memoizeStore() = MemoizeStore()  // ← 同样的 bug
```

`MemoizeStore()` 每次都 `new` 一个空的 `mutableMapOf`。追踪执行链：

1. `MemoizedDataSource.resolve` 调 `env.memoizeStore()` → 拿到 **空的** store A → miss → 计算 → 存入 A
2. 下一次调用（哪怕是同一个 RuleEnv、同一个 Source）→ `env.memoizeStore()` → 拿到 **全新的空** store B → **又 miss**

**结论：整个 memoize 缓存是空转的，零命中。** 你说的"现状没法引用同一份"——现在确实没法，因为缓存根本没工作。

更严重的是：TRACKER.md 声称"新增 `MemoizeCacheTest.kt`（7 用例）"，但 **这个文件根本不存在**（我搜索了整个项目）。跨规则树复用的端到端测试从未写过，所以这个
bug 从 7-20 实施至今没人发现。

## 三、评估：有没有必要

### 你的真实需求拆解

你说"DataSource, Transform, Operator, 参数都一样，现状没法引用同一份"，这其实对应两个不同层面的问题：

| 层面       | 痛点                                             | 对应方案                                               |
|------------|--------------------------------------------------|--------------------------------------------------------|
| **配置层** | 同一条管道链在 N 棵树里重复声明，改一处要改 N 处 | D-10（配置层 PipelineRef 命名引用），已被判 YAGNI 搁置 |
| **运行时** | 同一条管道链被重复计算 N 次，浪费性能            | D-9（运行时 memoize 缓存），就是现在的方案             |

### 运行时 memoize 有没有必要？我的判断是： **当前规模下没有必要，复杂度收益比太差**

**理由 1：性能问题尚未存在**

- 每回合评估约 5-10 张手牌，每张过几棵规则树，总共约 20-50 次管道执行
- Source 的实际计算：`env.warInfo().getPlayCards()` 返回引用、`env.matchState().allGroupPlayCounts()` 返回 Map——都是微秒级
- Transform 的实际计算：对 5-10 张卡的 filter/sum——微秒级
- **整个一回合省下来的时间可能不到 0.1ms**，而炉石每回合决策窗口是 75 秒

**理由 2：复杂度极高，且已证明不可控**

- `identityHashCode(input)` 做 cacheKey 是个脆弱技巧：依赖"Source 必须 memoize 才能给 Transform 提供 stable
  reference"这个隐式契约
- `dependsOnCallCard` 默认 false 是个脚枪：忘记声明 → 跨卡错误复用 → 产生错误结果（静默失败，最难查）
- **证据**：实施后声称"全绿"，但核心机制完全空转，6 天没人发现——这说明复杂度已经超出了可验证范围

**理由 3：T-127 的设计目标与你的真实需求错配**

- T-127 解决的是"运行时重复计算"（性能），通过 cacheKey 间接命中
- 你说的"引用同一份"更像是想要 **显式的、可读的共享**——"这两棵树用的是同一条管道"，这是 D-10 的领域
- cacheKey 命中是隐式的、不可观测的：你没法从配置上看出"这两棵树复用了同一条管道"

### 我的建议

**短期（立刻做）**：二选一

| 选项                | 做法                                                                                                                    | 适用场景                                                                        |
|---------------------|-------------------------------------------------------------------------------------------------------------------------|---------------------------------------------------------------------------------|
| **A. 删掉 memoize** | 移除 `MemoizeCache.kt`、接口上的 `memoize`/`dependsOnCallCard` 属性、所有组件的 `memoize=true` 标注。回到纯函数直连调用 | 如果性能没实测瓶颈，推荐这个。删掉 ~50 行基础设施 + 24 个组件的标注，复杂度归零 |
| **B. 修 bug 保留**  | 把 `memoizeStore()` 改成返回同一实例（`private val memoizeStore = MemoizeStore()`），补上缺失的 7 个测试                | 如果你确实观察到性能问题且能量化                                                |

**长期（当"配置冗余"真的变成维护痛点时）**：启动 D-10

- 在配置层给 PipelineRef 命名，多棵树按名字引用同一条管道定义
- 这直接解决"改一处要改 N 处"，而且可观测、可维护
- 触发信号：出现"同一条管道链在 ≥3 棵树里重复声明"的实际情况

---

**我的倾向**：选 A（删掉）。理由是这个机制设计的复杂度（identityHashCode 级联、stable reference 隐式契约、dependsOnCallCard
脚枪）远超它能带来的收益，而且它已经证明自己难以正确实施和验证。等真正遇到性能瓶颈再加一个简单的"评估级 Map<cacheKey, Any>
"就够了，不需要 per-component 装饰器这一层。
