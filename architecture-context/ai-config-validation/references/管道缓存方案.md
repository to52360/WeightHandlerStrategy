# 管道缓存方案（闭包层分段内容哈希缓存与 crossCard 开关）

## 一、核心原则

1. **绝对不在数据层/组件层感知缓存**：`DataSource`、`Transform`、`Operator` 保持纯函数与接口零侵入，不知道也不管缓存机制。
2. **缓存要素全在闭包层**：`PipelineAssembler.assemble` 与 `ScoreCompiler.compileSourceScore` 闭包同时拥有 `env`（含
   `evalCache`）和管道全貌及步骤位置，在此处统一管理缓存。
3. **正确性与性能彻底解耦（`crossCard` 维度）**：
    - **`crossCard = false`（默认值）**：不开启缓存，走直连评估（`source.resolve` + `transform.transform`），零 Map
      查找/字符串拼接开销，100% 绝对安全且无脚枪风险。
    - **`crossCard = true`（显式开启）**：针对全局对局/事件状态管道（如 `match_activity_events` ->
      `weighted_activity_sum` -> `gte(4)`），开启闭包层分段内容哈希缓存，在同一 `RuleEnv` 评估周期（多张手牌轮询评估）内实现
      100% 跨卡复用。
4. **内容哈希替代 `refId`**：当 `crossCard = true` 时，Key 使用 `sourceId + transforms 序列内容(含args)` 的规范哈希。不同
   `PipelineRef` 实例只要逻辑全同，即可 100% 命中缓存。
5. **共享前半段分段缓存**：每经过一个 Transform 步骤，Key 追加该步内容哈希 `env.cache(stepKey) { transform(...) }`。共享前
   N 步的前半段管道自动复用历史计算结果。

## 二、数据结构定义

```kotlin
data class PipelineRef(
    val sourceId: String,
    val transforms: List<TransformCall> = emptyList(),
    val operatorId: String,
    val operatorArgs: Map<String, Any> = emptyMap(),
    val crossCard: Boolean = false, // 🆕 默认为 false，向下兼容所有现有 DB/JSON 记录

data class SourceScore(
    val sourceId: String,
    val transforms: List<TransformCall> = emptyList(),
    val operatorId: String,
    val operatorArgs: Map<String, Any> = emptyMap(),
    val crossCard: Boolean = false, // 🆕 默认为 false

```

## 三、运行时求值流程

```kotlin
return { env ->
    if (!ref.crossCard) {
        // crossCard = false：直连求值，零 cache 开销
        var currentVal: Any = source.resolve(this, env)
        for ((transform, args) in transformInstances) {
            currentVal = transform.transform(currentVal, args)
        }
        operator.evaluate(currentVal, parsedOperatorParameter)
    } else {
        // crossCard = true：闭包层内容哈希分段缓存
        var currentVal: Any = env.cache(sourceKey) {
            source.resolve(this, env)
        }

        for (i in transformInstances.indices) {
            val (transform, args) = transformInstances[i]
            val stepKey = stepKeys[i]
            currentVal = env.cache(stepKey) {
                transform.transform(currentVal, args)
            }
        }

        operator.evaluate(currentVal, parsedOperatorParameter)
    }
}
```

## 四、跨决策复用与 playEventVersion 闲置结论

### 现状

管道级缓存走 `RuleEnv.cache`（`WarInfoEnv.evalCache`），生命周期 = `RuleEnv` = 一次决策（`processWeight` 内创建、回收，见
`WeightHandlerDomain.kt:64`）。

- **一次决策内**：`canUseCards.forEach` 共用同一 `RuleEnv`，`evalCache` 跨卡复用 ✅
- **跨决策**：`RuleEnv` 回收，所有管道重新评估 ❌

`PipelineCache`（整局级，`MyWarManage.pipelineCache`，`GameLifecycle` 管理）当前 **闲置**——`PipelineCache.kt:13` 注释明示"不与
`RuleEnv.cache` 共享实例"。`MatchState.playEventVersion` 的唯一消费方是 `PipelineCache`，故 `playEventVersion` 当前为
**无消费方死代码**（保留备用，非删除）。

### 跨决策复用的正确性障碍

启用 `PipelineCache`（整局级）+ `playEventVersion` 失效做跨决策复用，只对 `crossCard=true` 管道有意义。但这些管道的 source
不只依赖 MatchState：

`MatchActivityEventsSource`（`DefaultDataSources.kt:184-187`）：

- `matchState.playedCards()` ← `playEventVersion` 覆盖 ✅
- `warInfo.getGraveyardCards()` ← **无版本号覆盖** ❌

墓地卡牌会因随从死亡变化（不走 `recordCardPlayed`）。`WarViewSource` / `board_cards` 等 source 依赖战场局势（敌方出牌、场面变化），这些
`WarInfo` 变化 **全都没有版本号**。

故整局级 cache 对依赖 `WarInfo` 的 source 不安全（会用到过期数据）。`playEventVersion` 只能保护纯 MatchState 驱动的
source，适用面太窄。

### 结论

保持现状（`evalCache`，`RuleEnv` 级，一次决策回收）。理由：

1. 一次决策内跨卡复用（`canUseCards.forEach` 共用 `RuleEnv`）是最密集的重复计算场景，`evalCache` 已覆盖。
2. 跨决策复用收益边际（连续两次决策间通常已出牌 → `playEventVersion` 变 → 失效），且 `WarInfo` 无版本号是硬障碍。
3. `playEventVersion` + `PipelineCache` **保留备用**：等未来给 `WarInfo` 加版本号（捕获战场/手牌/墓地变化）后再考虑跨决策复用。

**触发重新评估的信号**：`WarInfo` 引入版本号 + 出现"同回合内连续多次决策且 MatchState 不变"的高频瓶颈场景。
