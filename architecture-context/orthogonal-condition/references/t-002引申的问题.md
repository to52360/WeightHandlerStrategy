问题:and和or的情况又怎么处理,有时算分,有时是控制
`AND/OR` 不应该自己决定“算分还是控制”。它们应该继承所在树的语义。

也就是说，你现在其实有两种树语义：

```text
EvaluatorTree：评分树
- Leaf -> RuleLogic
- AND -> 分数累加 / 遇 Prune 停
- OR -> 选择第一个可用分支
- Branch -> 用条件控制路线，但最终还是产出 RuleResult

ConditionTree：控制树 / 布尔树
- Leaf -> ConditionLogic
- AND -> all
- OR -> any
- NOT -> !
- Branch -> if condition then trueSubtree else falseSubtree
```

问题不是 `AND/OR` 要怎么特殊处理，而是**同一个节点结构被两个语义解释器复用了**。

所以建议是：

### 1. 评分树里的 AND/OR

保持现在这种 `RuleResult` 语义：

```text
AND:
- 子节点都 Continue -> 分数相加
- 任一 Prune -> 整个 AND Prune

OR:
- 返回第一个 Continue 分支
- 全部 Prune -> Prune
```

这里 `AND/OR` 是评分组合器。

### 2. 控制条件里的 AND/OR

走 `ConditionTree`，保持 Boolean 语义：

```text
AND:
- 所有条件 true -> true
- 任一 false -> false

OR:
- 任一条件 true -> true
- 全部 false -> false
```

这里 `AND/OR` 是条件组合器。

### 3. Branch 的控制条件必须引用 ConditionTree，而不是 EvaluatorTree

如果 Branch 需要复杂控制条件，比如：

```text
(手牌数 >= 3 AND 场上有龙) OR 当前费用 >= 5
```

那它应该绑定一个 `CONDITION_TREE`，而不是在评分树里用 `AND/OR` 临时解释成控制。

也就是：

```text
Evaluator Branch
  condition = ConditionTreeConfig
  onTrue = EvaluatorTreeNode
  onFalse = EvaluatorTreeNode
```

### 4. “条件算分”仍然放在评分树叶子

如果你想：

```text
条件 A 命中 +2
条件 B 命中 +3
条件 C 未命中 -1
```

那它是评分树：

```text
EvaluatorTree AND
  CONDITION A as score leaf
  CONDITION B as score leaf
  CONDITION C as score leaf
```

此时 `AND` 表示“这些评分项一起计算”，不是 Boolean AND。

所以要避免这种混用：

```text
EvaluatorTree AND
  既想当 Boolean 控制
  又想当 score 累加
```

这会一直混乱。

最终收敛一句话：

**AND/OR 没有固定语义，语义由所在树决定。评分树的 AND/OR 是 RuleResult 组合；条件树的 AND/OR 是 Boolean 组合。Branch 控制位只能吃
ConditionTree / Condition，不吃 EvaluatorTree。**

表达成**评分树里的一个专用评分叶子**，不要把它塞进 `ConditionTree` 的 `AND/OR` 语义里。

你要的不是：

```text
条件树返回 Boolean
```

而是：

```text
一组条件 -> 命中数量 -> 分数
```

所以它应该是 `RuleLogic`，不是 `ConditionLogic`。

模型可以叫：

```text
CONDITION_GROUP_SCORE
```

或者更通用一点：

```text
CONDITION_AGGREGATE_RULE
```

它的配置大概是：

```json
{
  "sourceType": "CONDITION_AGGREGATE",
  "sourceId": "matched_count_score",
  "weight": 1.0,
  "args": {
    "conditionTreeId": "dragon_combo_requirements",
    "scorePerMatch": 2.0,
    "minMatchCount": 0
  }
}
```

但注意：如果只引用一个完整 `ConditionTree`，你只能得到 true/false，拿不到“里面命中了几个”。所以“按个数算权重”需要的不是普通布尔编译器，而是一个
**计数解释器**：

问题:那怎么表达之前的满足条件,按个数算权重的关系

```kotlin
fun ConditionNode.countMatches(context): Int
```

语义可以定成：

```text
Leaf:
- true -> 1
- false -> 0

AND / OR:
- 不做短路
- 遍历所有子节点
- 返回子节点命中数之和

NOT:
- 一般不建议参与计数
- 或明确规定 true -> 1, false -> 0

Branch:
- 只统计实际走到的分支
- 或禁止出现在计数条件组里
```

更稳的是别复用普通 `ConditionTree`，单独建一个“条件组”：

```kotlin
data class ConditionScoreGroup(
    val conditions: List<ConditionPayload>,
    val scorePerMatch: Double,
    val minMatchCount: Int = 0,
    val maxScore: Double? = null
)
```

运行时：

```kotlin
val matchedCount = conditions.count { conditionRegistry.build(it)(context) }

if (matchedCount < minMatchCount) {
    RuleResult.Prune
} else {
    RuleResult.Continue(score = matchedCount * scorePerMatch)
}
```

这样表达最清楚：

```text
不是 A AND B AND C
而是 count(A, B, C) * scorePerMatch
```

如果以后需要更复杂的权重关系，可以扩展成：

```json
{
  "aggregation": "MATCHED_COUNT",
  "scoreFormula": {
    "type": "LINEAR",
    "base": 0,
    "perMatch": 2.0,
    "max": 6.0
  }
}
```

我建议当前最小实现就是：

```text
ConditionAggregateRule
- conditions: List<ConditionPayload>
- minMatchCount
- scorePerMatch
- mismatchScore
```

它属于 `RULE` / `Evaluator` 层，不属于 `Condition` 层。

一句话：  
**“满足条件按个数算权重”不是条件树，是评分规则；它内部复用条件，但输出 RuleResult。**
