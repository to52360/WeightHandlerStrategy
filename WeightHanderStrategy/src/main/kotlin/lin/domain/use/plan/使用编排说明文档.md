# 使用编排说明（use.plan 模型）

> 出牌编排域的说明文档。回答「一轮出牌的顺序怎么定、怎么调」。
> 选牌评分（combo 加权/互斥）不在此文档范围，见选牌域。

## 一、四载体分工（总览）

| 载体          | 表达                     | 落点                                                 |
|---------------|--------------------------|------------------------------------------------------|
| **绝对波段**  | 这张牌大概什么时候出     | `UseStage`（时序命名，先后可配）                     |
| **相对顺序**  | A 组的牌恒先于 B 组      | `ComboPlanDefinition.relation`（纯排序配方，见 §四） |
| **条件/收益** | 什么局面下这张牌值多少分 | 评估树 + 逐张 replan 涌现                            |
| **信息优先**  | 先过牌/先解牌            | 标签 `defaultOrderWeight`（T-030）                   |

## 二、排序主链（UsePlanOrderer）

```
stage 排序值（可配）→ orderWeight（降序）→ 兜底键（载体+方向均可配，默认 树分→baseValue 降序）
```

1. **stage**：时序枚举 `FIRST / SETUP / MID / LATE / GENERAL / LAST`。 先后 **不绑定枚举声明顺序**，由 `engine.properties`
   的 `stage.order` 配置 （`阶段:值` 逗号分隔，越小越先出；未列出回落 ordinal，默认 ≡ ordinal）。 例：控制卡组「保命先于解场」→
   `stage.order=FIRST:0,LATE:1,SETUP:2,MID:3,GENERAL:4,LAST:5`。
2. **orderWeight**：同段内人工偏好，降序。来源优先级 `显式配置 > 标签默认 > 0`， 显式配 0 可覆盖标签默认（null 表未配置，不做
   0.0 哨兵）。
3. **兜底键**：同段内 stage / orderWeight 都分不出先后时的最后 tie-break， **是同段内顺序的实际主导键**
   （7 条标签规则里 6 条 `defaultOrderWeight=0`，分组 override 大多不配）。载体是有序链，方向作用于整条链：

   | 配置项                      | 取值                       | 语义                                                            |
      |-----------------------------|----------------------------|-----------------------------------------------------------------|
   | `order.fallback.key`        | `tactical`（默认）         | 链：`评估树分 降序 → baseValue 降序`。战术分高的先出（**压过**物理价值），树分并列或为 0 退回价值锚 |
   |                             | `base`                     | 只看 `baseValue`：费量纲物理价值，构造期固定，与局面无关 → 最可复现 |
   |                             | `weight`                   | `powerWeight`：旧行为（baseValue+树分+光环+legacy+常数），一标多义，仅作 A/B 回退通道 |
   | `order.fallback.direction`  | `desc`（默认）             | 链上各档均为降序（旧行为）                                        |
   |                             | `asc`                      | 链上各档均为升序——逐张 replan 下保留剩余费用弹性（延后承诺）      |

   **为什么默认档是 `tactical`**：它让「评估树判定此刻有用的牌自动排到同段前面」， 无需逐卡配
   stage/orderWeight——这是编排工作量的主要来源。 **为什么不是 `weight`**：`powerWeight` 里只有树分对「谁先出」有贡献，光环分与先后无关、
   `BaseWeight(+1)` 是常数（对相对序零影响）、legacy handler 分量纲未知（可能几十分）会压倒一切。 **为什么是分层而非合成**（如
   `surplusFillValue = E + ts×scale`）：分层只用树分的 **序数**（谁更命中）， 合成要用 **基数**（具体几分）。树分跨卡可比目前是未验证假设，标差
   2 倍时合成体会翻转顺序而分层不会； 待 Q-024 评估树量纲费化落地后再考虑合成。

   > 方向仍未实战校准（`use-intent-model/K-001`）：desc = 高价值先落袋防中断，asc = 保留费用弹性。
   > 战术层默认启用同样未经校准（`K-002`）。两档配置即为校准手段。

### 标签默认（全局兜底层）

| 标签       | stage   | orderWeight | N（惜售） | replan |
|------------|---------|-------------|-----------|--------|
| SAVE_LIFE  | LATE    | 0           | 1         | —      |
| CLEAN      | MID     | **1**       | 1         | —      |
| GREED      | SETUP   | 0           | —         | —      |
| DRAW_CARD  | MID     | **0**       | —         | —      |
| VALUE      | GENERAL | 0           | —         | —      |
| EXTRA_COST | GENERAL | 0           | —         | —      |

行为涌现：同在 MID 段时 **解牌 (1)先于过牌 (0)**；解牌不行则先过牌，抽到新牌经 replan 重规划。 N=1
仅保留给「晚出可能更有价值」的标签（SAVE_LIFE/CLEAN）；
`replanAfterUse` 标签兜底与卡级/分组级取 **OR**（清场改变战场但手牌数减少，
`isChangeByUseSuccess` 靠手牌数量推断会漏判，故需显式声明）。

> **EXTRA_COST 特例（D-019）**：特殊查询牌——持有者由 `ExtCostStrategy` 接管（额外费用双世界比较，
> 出牌时机写死在 find 阶段先于组合，不进 UsePlanOrderer），表中 stage/orderWeight **不被消费**，
> GENERAL 仅作意图模型的惰性默认落点。机制牌（硬币）由 `COINProvide.mechanismPurposes` 启动期
> 硬编码注入该标签，不依赖 DB 配置。

## 三、意图推导链

```
CardUseConfig（标签 + stageOverride? + orderWeight? + replanAfterUse）
        ↓ UseIntentDeriver（逐字段独立解析：显式 > 标签默认 > 内建兜底）
UseIntent(stage, orderWeight, replanAfterUse, ...)
```

- 分组级 `GroupUseOverride`（stageOverride/orderWeight/conditionalStage）经
  `UseIntentAssembler` 合入 `CardUseConfig`。
- `conditionalStage`：条件命中→改 stage（条件树 conditionId 引用）。 **只条件化 stage，不含 orderWeight**（条件化完整排序挂起
  Q-035）。
- 单卡无独立编排载体（Q-031 挂起）：调单卡时机需打标签（继承全局默认）或建组（分组 override）。

## 四、纯排序配方（重点）

**需求**：只表达「A 组的牌恒先于 B 组」，不加分、不互斥。

**配方**：`score = 0` + `coreMutex = false` + `relation = CORE_BEFORE_DEP / DEP_BEFORE_CORE`

```json
save_combo_plan({
  "managerId": "xxx",
  "coreGroupIds": ["铺场组"],
  "depGroupIds": ["清场组"],
  "score": 0,
  "coreMutex": false,
  "relation": "CORE_BEFORE_DEP"
})
```

**⚠️ coreMutex 陷阱（默认 true）**：不显式置 false 时，多核心组会被互斥剪枝、 只剩一组参与排序——纯排序场景下这是最常见的配置错误。

**与 orderWeight 的区别**：relation 是拓扑约束，跑在基础序之上， **可跨阶段拉动**
（把 LATE 的牌拉到 FIRST 之前也行）；orderWeight 只管同段内。注意阶段因此 **不是硬边界**。

**边界**：约束只在本批次（UsePlan）内生效；某张牌打出后 replan 重建批次，约束随新批次重算。

## 五、两条出牌路径与「排序单点」原则（T-038）

一轮出牌有两条会真正打牌的路径，二者 **必须**都走 `UsePlanOrderer`，否则四载体在漏掉的那条上静默失效：

| 路径                                 | 触发条件                   | 牌集合               | 排序                                              |
|--------------------------------------|----------------------------|----------------------|---------------------------------------------------|
| **主组合** `useCombo`                | 每轮必然                   | 选牌层确定的一组牌   | `UsePlanOrderer.order(usePlanBuilder.build(...))` |
| **失败补偿** `compensateFailedCards` | **有牌打失败**（`FAILED`） | 落选卡过滤后的候选池 | 同左（T-038 起；此前是裸 `powerWeight` 降序）     |

**补偿的触发条件（T-038b/D-024）**：`useCombo` 返回三态 `UseComboOutcome`
（`COMPLETED` / `REPLANNED` / `FAILED`）， **只有 `FAILED` 才补偿**：

| 结果        | 含义                               | 是否补打                                 |
|-------------|------------------------------------|------------------------------------------|
| `COMPLETED` | 全部打出成功，或组合为空           | 否                                       |
| `REPLANNED` | 某张牌打出后触发 replan 并已重规划 | 否——批次由重规划接管，补偿会与新批次打架 |
| `FAILED`    | 有牌打失败且未触发 replan          | **是**                                   |

此前 `useCombo` 只返回 Boolean（`true`=已 replan），`false` 同时表示「全成功」和「有失败但没 replan」， 导致 **只要没 replan
就必然补打** —— 补偿路径兼做了余费填充兜底。余费填充的正牌载体是选牌层
`fillSurplusCost`（D-004），补偿回归「补偿」本职即可。

差异仅在于 **打出方式**：主组合是「一组确定的牌逐张打出」；补打是「能打就打的候选池」—— 循环内保留
`card.cost() > 剩余费用 → continue` 实时校验，费用不够就跳过而非终止。 **排序本身仍是一次性完成**
（基于补打开始时的战场快照），不逐张重排：与主组合「先排后打」对称， 且避免 relation 约束在批次内随战场漂移（同一批牌先后中途翻转会让顺序不可推理）。

> **排序单点原则（D-023）**：排序语义由 `UsePlanOrderer` 单点承载。
> 任何新增出牌路径都须复用它， **禁止**在调用侧另写 `sortedBy...` / `maxBy...`——
> 那是给四载体开后门（补打路径曾因此让「CLEAN 先于 DRAW_CARD」「A 组先于 B 组」全部失效）。

## 六、手牌查询配方（条件/评估树输入）

正交管道两步配出「手牌里有没有某类牌」：

```
hand_combo_cards → purpose_filter(tagId=FINISH) → is_not_empty   「手牌有斩杀牌吗」
hand_combo_cards → has_card_feature(feature=TAUNT)               「手牌有嘲讽牌吗」
```

- `purpose_filter` 按用途标签过滤（FINISH 已收窄为纯查询标签，无编排映射）。
- `has_card_feature` 按卡牌特征判定（嘲讽/亡语/圣盾/冲锋/突袭/吸血/复生/风怒/剧毒/ 潜行/战吼/发现/法强/冻结/免疫/扰魔/星舰，可选值
  dataSource=`card_features`）。
- 这些查询可作条件树条件或评估树输入，实现「有斩杀牌才打斩杀组合」类策略。

## 七、已知边界与陷阱

| 项                          | 说明                                                                                                                                                 |
|-----------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------|
| `LAST` 只保证**本批次**最后 | replan 重建批次后约束重算；「整回合最后」需 replan 语义配合                                                                                          |
| relation 跨批失效           | 同上，A 打出后 B 若落选新批次，约束消失                                                                                                              |
| `mustAdjacent` 未消费       | 引擎侧不生效（需先设计组块/窗口模型），配置面已标注禁用                                                                                              |
| 同属约束两侧分组的卡        | 约束对它静默失效（既不算 before 也不算 after，无边生成）                                                                                             |
| 排序追溯                    | `lin.domain.use.plan` 调 debug 可看逐卡 stage/orderWeight/baseValue/powerWeight + 兜底键载体与方向 + 生效约束边                                      |
| 兜底键方向                  | 默认 `desc`（贵的先出，历史行为），方向未实战校准；`asc`（便宜先出，保留费用弹性）待对比后定                                                         |
| 兜底键战术层                | 默认启用（树分高的先出），未实战校准；想只按物理价值排 → `order.fallback.key=base`，想完全回退 → `=weight`                                           |
| 战场快照                    | 评估与排序共享 `warManage.ruleEnv` 同一批次快照；出牌（`tryUseCard`）与 `reLoad` 均使其失效重建——新增绕过这两处的战场变更路径必须补失效点（`K-003`） |
| 补打批次排序                | 一次性排序（不逐张重排）；打出方式仍是「能打就打」，费用不够跳过。补打池仅 1~3 张，顺序差异影响有限                                                  |
